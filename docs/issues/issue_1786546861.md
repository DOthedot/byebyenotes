# Code-review findings — 2026-08-12

**Scope:** Whole repository review: client state/rendering, serverless APIs,
dependencies, and test configuration.

**Status:** Open. No code changes were made as part of this review.

## High

### 1. Malformed shared URLs can crash the application

**Status:** `open`

`loadState()` checks only that `state.blocks` is a non-empty array before mapping
over entries and reading `b.type` / `b.lang`. A crafted URL state containing
`blocks: [null]` throws. Non-string `content` can later throw in markdown
rendering. This also affects tiny links because tiny resolution verifies only
that `decodeState()` returns an object before it calls `loadState()`.

**Evidence:** [app.js](../../app.js:2425), [app.js](../../app.js:2439),
[app.js](../../app.js:2549)

**Recommended fix:** Add one state-normalization/validation boundary before any
rendering. Accept only text/code blocks, coerce or reject non-string content,
allow only known language strings, bound the number and size of blocks, and show
the existing invalid-link state instead of throwing.

**Verification:** Add tests for null, primitive, missing, and wrongly typed
blocks in normal hashes and tiny-link resolution.

### 2. Image storage is publicly writable and permanent

**Status:** `open`

`POST /api/img` accepts uploads without authentication, rate limiting, quota, or
ownership checks. Stored images do not expire. An attacker can repeatedly write
up to the configured payload limit, exhausting KV capacity and incurring cost.

**Evidence:** [api/img.js](../../api/img.js:38), [api/img.js](../../api/img.js:44)

**Recommended fix:** Add a rate limit and an ownership/authorization mechanism;
give images an expiration or implement bounded cleanup/quota enforcement.

**Verification:** Add API tests for rejected over-limit/rate-limited uploads and
for the selected expiration/ownership behaviour.

## Medium

### 3. Random short IDs can silently overwrite existing tiny links or images

**Status:** `open`

Tiny-link and image IDs are made with `Math.random()` and then written with an
unconditional Redis `SET`. Neither endpoint uses cryptographically strong
randomness nor verifies that its generated ID is unused. A collision overwrites
the prior object, corrupting an existing tiny link or image.

**Evidence:** [api/tiny.js](../../api/tiny.js:43), [api/img.js](../../api/img.js:44)

**Recommended fix:** Generate IDs with `crypto.randomBytes`, create records with
Redis `SET ... NX`, and retry a bounded number of times when a collision occurs.

**Verification:** Unit-test a simulated collision and confirm no existing value
is replaced.

### 4. Cross-device sync is a bearer-key scheme, not encrypted sync

**Status:** `open`

The client uses a fast, unsalted SHA-256 of a minimum six-character passphrase
as the API credential and stores it in `localStorage`. Notes are sent as readable
JSON to KV. Anyone who obtains or guesses the derived key can read and overwrite
the synced data.

**Evidence:** [app.js](../../app.js:340), [app.js](../../app.js:388),
[api/sync.js](../../api/sync.js:36)

**Recommended fix:** If private sync is a product requirement, derive a key using
a password KDF and encrypt sync payloads client-side; rate-limit the API and make
the UI/docs explicit about the security model.

**Verification:** Add tests around encrypted payload handling and failed
authentication/rate limiting, if implemented.

### 5. Third-party script integrity protections are absent

**Status:** `open`

All CDN scripts run without Subresource Integrity. The `html-docx-js` URL is
also unversioned, so its contents can change without a repository change. A
compromised CDN dependency would execute with access to note data and the sync
key stored in the browser.

**Evidence:** [index.html](../../index.html:107)

**Recommended fix:** Pin every dependency version, add SRI plus `crossorigin`
where viable, and configure an appropriate Content Security Policy/security
headers.

**Verification:** Confirm the app loads with integrity checks enabled and that
the CSP permits only required resources.

## Low

### 6. Jest discovers duplicate tests in nested worktrees

**Status:** `open`

`npx jest` passes, but it runs tests from `.claude/worktrees/...` in addition to
the root suite (56 suites instead of the root repository's 16). This duplicates
coverage, slows verification, and risks unrelated worktree changes affecting
results.

**Evidence:** [package.json](../../package.json:1)

**Recommended fix:** Limit Jest discovery to the root `tests/` directory using
`roots` or `testMatch`.

**Verification:** `npx jest --listTests` should list only root-repository tests.

### 7. API handler coverage is incomplete

**Status:** `open`

The repository has direct handler tests for `api/tiny.js`, but not for
`api/img.js` or `api/sync.js`. The untested paths include their input validation,
KV error handling, response headers, and method handling.

**Evidence:** [tests/api-tiny.test.js](../../tests/api-tiny.test.js:1),
[api/img.js](../../api/img.js:21), [api/sync.js](../../api/sync.js:21)

**Recommended fix:** Add isolated handler tests for both APIs, covering each
supported and unsupported method, invalid input, storage failures, and headers.
